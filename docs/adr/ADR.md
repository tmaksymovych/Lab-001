##  1.Розуміння Задач

Для зручності, майбутнього маштабування на відказостійкості, сервера мають контролюватися через декларативно. Тобто без ручних налаштувань. (без ClickOps). Для початку треба визначити основі задачі проєкту:
- Регулювати VPC, SubNets, RT, Gateways, Security Gruops.
- Моделювати майбутні задачі, такі як: реплікація, телеметрія, обрахунки(compute)
- Працювати в середовищі aws academy lab, яке має обмеження щодо IAM (має обмеження по часу життя сессії, нестачі прав root та меж дозволів).

##  2.Вибір IaC

Наразі я маю 3 варіанти (окрім ClickOps), це: Terraform, CloudFormation та CDK (Cloud Development Kit).

Кожен із них має свої компроміси (trade-offs) у контексті наших вимог та обмежень пісочниці AWS Academy:

- AWS CloudFormation: Нативний інструмент AWS, який не потребує встановлення сторонніх бінарників і керує стейтом всередині самого хмарного провайдера. Має пряму підтримку Change Sets та Drift Detection у консолі. Проте його синтаксис (YAML/JSON) громіздкий, а процес відкату (rollback) стека у разі помилок прав доступу в пісочниці є повільним і сповільнює розробку.
- AWS CDK: Дозволяє описувати інфраструктуру повноцінними мовами програмування (TypeScript/Python). Забезпечує високу гнучкість, але створює надлишковий оверхед (потребує Node.js середовища, компіляції та синтезу в CloudFormation) і генерує складні для прямого аналізу шаблони, що ускладнює діагностику обмежень LabRole.
- Terraform: Декларативний інструмент із чітким HCL-синтаксисом, швидким паралельним виконанням та зручним попереднім переглядом змін (terraform plan). Дозволяє легко ізолювати заборонені в пісочниці ресурси IAM та забезпечує модульну структуру, що критично для масштабування системи від базової мережі в М1 до шардів і реплік у наступних етапах.

# Рішення:
 Обираємо Terraform як основний інструмент через швидкість зворотного зв'язку в CLI, зручність модульного поділу та простоту локального тестування інфраструктури без тривалих блокувань стека. (+ я мав досвід мінімальної роботи з terraform :) )

## 4.CIDR схема
буду працювати в stokholm(eu-north-1). Маски:
- для VPC беру стандартні 10.0.0.0/16 -> залишається 65,536 IP-адрес для внутршініх мереж.
- для підмереж беремо /24, що дає 256 всього або ж 251 вільний хост.

Для досягнення відмовостійкості, підмережі рознесені по двох фізично незалежних зонах. доступності (eu-north-1a та eu-north-1b) за семантичним принципом:

(* знов ідея Аргона)
Десятки в 3-му октеті визначають рівень безпеки (Tier): 0x — публічний шар, 1x — приватний шар даних, 2x — резерв під шар моніторингу.
Парність 3-го октету визначає зону доступності: непарні (1, 11) — зона eu-north-1a, парні (2, 12) — зона eu-north-1b.

| Назва підмережі | CIDR-блок | Зона (AZ) | Діапазон доступних хостів | Зарезервовані AWS адреси | Призначення |
| :--- | :--- | :--- | :--- | :--- | :--- |
| public-subnet-1 | 10.0.1.0/24 | eu-north-1a | 10.0.1.4 – 10.0.1.254 (251 IP) | .0, .1, .2, .3, .255 | Вхідний трафік, Coordinator |
| public-subnet-2 | 10.0.2.0/24 | eu-north-1b | 10.0.2.4 – 10.0.2.254 (251 IP) | .0, .1, .2, .3, .255 | Резерв Coordinator / ALB |
| private-subnet-1 | 10.0.11.0/24 | eu-north-1a | 10.0.11.4 – 10.0.11.254 (251 IP) | .0, .1, .2, .3, .255 | Ізольовані шарди БД та репліки |
| private-subnet-2 | 10.0.12.0/24 | eu-north-1b | 10.0.12.4 – 10.0.12.254 (251 IP) | .0, .1, .2, .3, .255 | Ізольовані шарди БД та репліки |

При такому розподіленні всі 4 підмережі сумарно використовують лише 1 024 адреси (
1.56% від ємності 10.0.0.0/16), залишаючи 252 вільних блоки /24 для подальшого масштабування системи.
